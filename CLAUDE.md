# TGS Caller CRM — Frontend

Call center CRM frontend (Next.js App Router). Backend is a separate sibling
repo (`tgs-caller-crm-be`, FastAPI) — check it for the authoritative API
contract (`src/schemas/`, `src/routers/`) before inventing request/response
shapes.

## Stack & requirements

- Next.js (App Router, Turbopack), React 18, TypeScript (`strict: true`),
  MUI (`@mui/material` v9 + `@mui/icons-material` + `@mui/material-nextjs`),
  Emotion, Tailwind CSS v3.
- **Node >= 20.9** is required — `nvm use 20` before running `npm run dev`; the
  system default may be Node 16, which fails silently-ish (no listening port).
- `msw` mocks the backend in the browser (`app/providers/MockProvider.tsx`
  starts the worker; handlers in `mocks/handlers.ts`). Use mocks to build UI
  ahead of backend endpoints — the real backend stubs unbuilt routes with 501.
- Path alias `@/*` → repo root (`./*`), covers `app/`, `lib/`, `components/`.
  Prefer `@/lib/...`, `@/components/...` over relative `../../` imports.

## API contract (OpenAPI → TypeScript)

Repos are separate: this frontend and `tgs-caller-crm-be`. The backend is
the sole source of truth for request/response shapes. It commits
`openapi/openapi.json`; this repo generates TypeScript from that file so the
FE never invents or hand-maintains a parallel OpenAPI document.

- **Generate / refresh:** `npm run gen:api-client` (also works as
  `pnpm gen:api-client`). Requires the backend repo as a sibling at
  `../tgs-caller-crm-be` (same parent folder as this repo).
- **Output:** `lib/generated/schema.d.ts` — auto-generated by
  `openapi-typescript`. Keep generated contract types under `lib/` with the
  rest of shared app code; do not revive a root-level `src/` only for this
  file. Do not edit it manually; regenerate after backend contract changes.
- **Command under the hood:**
  `openapi-typescript ../tgs-caller-crm-be/openapi/openapi.json -o ./lib/generated/schema.d.ts`
- **Workflow:** BE updates Pydantic schemas → `uv run python -m scripts.export_openapi`
  in the backend repo → run `gen:api-client` here → commit the updated
  `lib/generated/schema.d.ts`.
- **Consumption:** `import type { paths } from '@/lib/generated/schema'`.
  `lib/api.tsx` is a thin typed fetch helper over those types. Prefer them
  over inventing new hand-rolled DTO interfaces for frozen endpoints (auth,
  leads, qualification, transfers, dashboard live-status).

## Auth & role model — the core domain rule

**Role selection never happens client-side.** The backend is the only source
of truth for a user's role(s); the frontend just reacts to it. This is a hard
product requirement, not a style preference — don't add a role dropdown/toggle
anywhere, even for demos.

That rule is about somebody choosing **their own** role. An administrator
setting **someone else's** is a different thing entirely: it goes through
`PATCH /auth/users/{user_id}`, which the API authorizes and audits, and it lives
on `/admin/users` (see Users below). The role checkboxes there are the sanctioned
path, not an exception to this rule.

Contract (typed in `lib/generated/schema.d.ts`):

- `POST /auth/login` `{username, password}` →
  `{access_token, refresh_token, token_type, expires_in_min}` — the access token
  lasts 15 minutes, the refresh token 12 hours.
- `POST /auth/refresh` `{refresh_token}` → a new pair. **Rotated on every use:**
  presenting a spent refresh token is treated as theft and ends every session of
  that user, so a refresh token must never be sent twice.
- `POST /auth/logout` `{refresh_token}` → 204, whether or not the token was live.
- `GET /auth/me` (Bearer token) → `{id, username, email, name, active, roles, team_id, created_at}`.
  `email` may be null and is never shown: people sign in by username.
- `RoleName = "fronter" | "closer" | "administrator" | "qa_manager" | "qa_agent" |
  "retention" | "super_admin"`. A user can hold multiple roles; frontend picks the landing
  route by priority (`super_admin` > `administrator` > `qa_manager` > `closer` >
  `fronter` > `qa_agent` > `retention`), see `lib/auth.ts`. There is no QA Lead: that role was
  merged into QA Agent.
  Super Admin inherits every Team Admin `/admin` surface (`roleSatisfies`).
- Every error response is `{detail, code, fields?}`, read with `readApiError()`.
  Branch on `code`, never on `detail`: `auth.not_authenticated` (token missing,
  invalid or expired), `auth.invalid_credentials`, `auth.invalid_refresh_token`,
  `auth.forbidden` (wrong role), `validation_error` (with `fields`).

Frontend pieces:

- `lib/auth.ts` — `login()`, `refreshTokens()`, `revokeRefreshToken()`,
  `getCurrentUser()`, `landingRouteForRoles()`, and session storage in
  `localStorage`: `tgs_crm_access_token`, `tgs_crm_refresh_token`,
  `tgs_crm_access_expires_at`. Every data call reads the access token with
  `readToken()` when it sends — a poll on every tick, never once for later.
- `lib/sessionStore.ts` — the same session in IndexedDB, the copy renewals trust.
  A tab's `localStorage` can lag another tab's write long enough to replay a spent
  refresh token, which the API answers by ending every session; IndexedDB doesn't.
- `lib/session.ts` — `refreshSession()` renews once however many callers ask:
  shared within a tab, and across tabs through a Web Lock, because of rotation.
  `withSession(call)` renews once on `auth.not_authenticated` and retries.
  `signOut()` clears the session at once, then revokes the refresh token on the
  server without waiting.
- `components/auth/SessionKeeper.tsx` — mounted once in `AppProviders`. Renews the
  access token about a minute before it expires (and on focus, since timers stop
  while a laptop sleeps). Sends this tab to `/login` when the session ends: another
  tab signs out, or a renewal anywhere in this tab finds it over (`lib/session.ts`
  fires `SESSION_ENDED`). Nothing keeps running without a session.
- `lib/apiError.ts` — `readApiError(res)` reads any failed response into
  `{status, code, message, fields}`.
- **Why localStorage and not an httpOnly cookie:** the API hands tokens back in
  the response body, authenticates with `Authorization: Bearer`, sets no cookie
  and doesn't allow credentialed cross-origin requests — so a cookie the browser
  kept wouldn't be sent with a call anyway. The cookie-plus-Proxy pattern in
  Next's authentication guide would route every data call through Next — a
  separate decision, not a storage tweak.
- `components/auth/RequireRole.tsx` — client guard wrapping a page's content;
  redirects to `/login` if there's no token, the token is invalid, or the
  resolved roles don't include the required one. `RequireAuth` is the same
  but accepts any authenticated role, for a screen every role may see (none
  today).
- Every role-landing page (`app/fronter`, `app/closer`, `app/admin`) wraps its
  body in `<RequireRole role="...">`. New protected routes must do the same —
  routes are open by default in Next.js, nothing blocks direct navigation
  unless a page explicitly guards itself.
- `/login` redirects an already-authenticated user straight to their landing
  route instead of re-showing the form.

## Desks and the sidebar

- Each role has a segment — `/fronter`, `/closer`, `/admin` — whose
  `layout.tsx` renders `Sidebar role="…"` around its pages; a role's other
  screens live beneath it (`/admin/reports`, `/closer/queue`).
- `components/dashboard/Sidebar.tsx` keeps a nav list per role: `deskNav()` for
  fronters and closers, `ADMIN_NAV` for administrators. Each item carries its
  own `isActive(pathname)`. A new page goes under its role's segment and into
  that role's list.
- **A Super Admin's list is `SUPER_ADMIN_NAV`**: Users, Teams, Campaigns,
  Reports, Policy lookup, Team stats, Agent stats, Retention, Card edit requests, QA and
  QA stats. A Team Admin's has Agent stats too. Reports is there because its drill-down is how they
  reach a lead's full view. Exceptions stays out: without the dialer it is empty.
- **QA desks.** A QA Manager works from `/admin` with QA, QA stats and Users. A
  QA Agent works from `/qa` with QA and QA stats (`qaDeskRole()`).
- **Retention desk.** Retention works from `/retention` with Pending and Upload
  (`retentionDeskRole()`). A Super Admin gets the same screens at `/admin/retention`.
- **Somebody may hold more than one role**, and the nav only ever shows the desk
  they are on, so the sidebar identity doubles as a desk menu — `heldDesks()` in
  `lib/auth.ts` lists every desk held, the current one ticked. A single-role
  account gets the identity exactly as it was: no button, nothing to click.
  Switching needs no state of its own, because the URL already decides the desk
  through `deskRoleFromPath()` — navigating *is* the switch.
- That menu is MUI's `Menu`, and it is the only floating panel in the app. It is
  MUI rather than hand-rolled for the reason `components/ui/Dialog.tsx` is:
  click-outside, Escape, focus restore and the ARIA roles come with it, and
  there is no click-outside or keydown machinery here to build on. It closes in
  each item's `onClick` rather than an effect on `pathname` — a synchronous
  `setState` in an effect is a lint error `Sidebar.tsx` already trips twice.

## Live data

The administrator dashboard (`/admin`) is fed by `lib/liveStatus.ts`:
`watchLiveStatus()` reads `GET /reporting/live`, then follows the
`/realtime/ws` socket, which pushes the whole snapshot every 15 seconds.

- The socket authenticates with a ticket from `POST /realtime/ticket`, and a
  ticket works once — mint a new one for every connection, reconnects included.
- The socket doesn't replay, so re-read the snapshot after every connect.
- A dropped socket reconnects with backoff; one silent for 45s (the server
  pings every 20s) is treated as dead.
- The server closes a socket once its user is no longer active, signed in, or
  allowed its channels (checked every 20s). The reconnect then fails, and the tab
  ends up at `/login` — or, for a lost role, the page clears and says so.
- Under MSW there's no socket to mock, so it polls the snapshot every 15s.
- "Live" means the newest snapshot arrived within three push intervals,
  timed by arrival — a socket kept open by pings can still carry stale figures.
- Times show in the user's own zone, with its abbreviation. The counters read
  `funnel_today_by_timezone`, which carries today in every zone a user can
  choose, so one push gives each viewer their own day.

## Fronter desk

`/fronter` (`components/fronter/FronterDeskScreen.tsx`) is where a fronter works
leads by hand: New lead, and one Leads table, read from `GET /leads/search`
through `searchLeads()` in `lib/leads.ts`.

- **The list is every lead the team ever saved as Callback, and nothing else.** A
  lead stays on it once it is transferred, accepted or sold, with Edit still
  there, as the client asked; its latest outcome shows in the table. Newest
  first. There is no outcome filter, and search stays inside the list.
- **A fronter records Callback or Transferred, and must pick one.** Transferred
  must name a closer, on a call or not. The offer waits in that closer's queue
  with no time limit until they accept it, and it cannot be rejected. The closers
  table shows how many offers each closer already has waiting.
- **No Search button.** The box searches 300ms after typing stops, from the
  first character, and matches part of the name, and part of the phone too when
  it is a number: one digit already searches phones, one letter names. A search
  with a letter in it stays on names, or its stray digits would match nearly
  every phone. A new search goes back to page one, and only the newest
  reply is drawn, so a slow one can't replace it. The table reloads every 30
  seconds: each load is a full query on a busy team.
- **The table is titled Callbacks,** so it never repeats the page's own "Leads".
- **Opening a lead creates nothing.** `LeadEditDialog` asks for a call through
  `openLeadCall()` (`POST /leads/{id}/calls`) only when a save records a
  disposition or a transfer. The backend answers with the lead's latest call
  while nothing is recorded on it or it waits on a callback, and a new call
  otherwise; New lead follows the same rule for a phone already on the team.
  A save that only edits the lead is a PATCH and nothing more, which is why the
  dialog starts with no disposition picked unless the lead is a callback.

## Fronter Active Call

Not linked from the desk or the sidebar since the dialer queue was removed.

`/fronter/workspace/?id=<interactionId>` is where a fronter works a call —
`components/workspace/ActiveCallScreen.tsx`, composing the checklist, the
disposition picker and the transfer panel.

- **Two actions, and both are always rendered.** Transfer to Closer, and Save &
  End Call. Most calls end without a transfer — no answer, voicemail, not
  interested — and the screen used to have no way to say so, which left those
  rows sitting in the queue forever. Disabled rather than hidden: a qualified
  lead with no closer free is refused by the server, and a fronter with nowhere
  to record that call would be left holding it.
- **The disposition decides which action is available**, through
  `allows_transfer` on the catalogue row. "A disposition is selected" used to be
  the whole check, which let "No Answer" be handed to a closer. The server
  enforces the same rule (`transfer.disposition_not_transferable`), so the
  client only decides what to offer.
- **Ending a call writes a qualification only when something was captured.**
  `consentFromActiveCall` stamps `consent_given` and `consent_captured_at` from
  the form's default, so saving an untouched form on a no-answer would assert
  consent was taken on a call nobody picked up. `hasCapturedSomething()` is the
  rule — and DNC always counts, because `consent_dnc` is the only place the
  suppression is stored.
- **Then the row leaves the queue**, through `PATCH /queue/fronter/{id}` with
  `left: true` (`leaveFronterQueue` in `lib/queue.ts`). A 404 doesn't fail the
  call: an interaction opened by direct link may have no open row, and the
  outcome is already saved by then.
- **DNC is two controls because it is two facts.** The checkbox is a standing
  instruction about the lead and is what the transfer gate reads; the "Do Not
  Call" disposition is what happened on this call. Picking that disposition
  ticks the checkbox and locks it — the outcome cannot coexist with a record
  saying the lead is still callable — but moving off it leaves the flag alone,
  since un-ticking a suppression the fronter just asserted is the one direction
  that loses something.

## Closer cart

`components/closer/CartPaymentCard.tsx`, above the closer's disposition card;
the API calls and rules are in `lib/cart.ts`. Screens say **card**, as the client
does. The code, the API and the database keep `cart`.

- **Unlocks once the transfer is accepted.** Before that the API would refuse
  the save: only the closer who accepted the call may write its cart.
- **Account, routing and CVV show only while focused**, and read `•••• 1234`
  (or `•••`) once the closer leaves the field. They live in component state
  alone, never storage or logs.
- **The account number spaces itself in fours** as it is typed
  (`formatAccountNumberInput`: digits only, at most 19), for any account, card or
  not. The caret stays where the closer is typing (`caretAfterDigits`), and once
  they leave the field it reads `•••• •••• •••• 4242`. The API gets the digits.
- **The full numbers never come back.** `GET /interactions/{id}/cart` gives at
  most the last four digits. A saved cart shows read-only, masked, with an
  **Edit card** button. In the form, a saved number shows as its placeholder
  (`•••• 4242`); left blank it is kept (the request leaves it out), and typing
  replaces it. The CVV is checked by the API and discarded.
- **Money goes as strings** (`"1800.00"`), formatted on blur and shown through
  `formatMoney`. `CURRENCY` in `lib/format.ts` is the one place the currency is
  set: the API stores amounts without one.
- `checkCart` mirrors the API's rules so most mistakes show inline before a
  save; the mock handler reuses it, so the two cannot drift.
- **A sale needs a saved cart.** The API refuses an outcome with `counts_as_sale`
  until the call has one, and `CloserDispositionCard` says so first: Save
  Disposition turns off with a short note. `cartSaved` is `null` until the cart
  has loaded, so a sold call doesn't flash the note and a failed load leaves the
  decision to the server. Other outcomes need no cart. The policy number stays
  optional, but the cart locks once a final outcome is recorded, so a sale saved
  without one can't be marked Paid; its hint says so. A number belongs to one
  sale: one already on another cart, in any case, comes back as a 422 on
  `policy_number` and shows under the field.

## Closer callbacks

The closer's Queue page lists **Callbacks** under the transfer queue
(`components/queue/QueueScreen.tsx`, `GET /queue/callbacks`): the calls this
closer accepted whose latest closer outcome is Callback Scheduled, oldest first.
Every row opens. The Card edit column shows where a request to change its saved
card stands (Waiting for approval, Approved, Rejected), or a dash.

- **Open goes back to the same call.** The workspace loads its cart and saved
  outcome, and saving another outcome records the next closer version on that
  call, which takes it off the list. No new call is made.
- **No clock on a call with an outcome.** The header timer counts from the
  accept, so it shows only while the call is still being worked.
- **It loads on its own and refreshes every 30 seconds**, so a queue error never
  hides it, and the reverse.

## The closed call and card edit requests

A closer's final outcome closes the call to them. `GET /interactions/{id}/dispositions`
carries `locked`, and `closedCall()` in `lib/closer.ts` turns it into a badge and one
line for the workspace.

- **A final outcome** locks the cart, the outcome and the fronter's details. The
  disposition card swaps its form for the saved outcome with a Closed badge, and the
  cart shows read-only (`CartPaymentCard readOnly`). The API answers a write with
  409 `interaction.locked`.
- **Callback Scheduled is not final.** The closer opens the callback straight from
  Callbacks and changes its outcome and details freely.
- **Changing the saved card on a callback needs a Super Admin.** The cart carries
  `card_edit`. `needs_approval`, `waiting` and `rejected` lock the account number,
  routing number and expiry: the card section shows them masked, with **Request to
  edit card** (a dialog with an optional reason, `POST
  /interactions/{id}/card-edit-requests`) or **Request again**. The policy number and
  amounts stay editable (**Edit payment**). `approved` opens the whole card for one
  save, which locks it again. While waiting, the panel checks every 30 seconds and
  when the window gets focus. A callback with no saved card takes a first one
  freely. The panel reloads after each outcome (`reloadKey`), since a callback is
  what locks it.
- **The list** is `components/callbacks/CardEditRequestsScreen.tsx` at
  `/admin/card-edits`: a Super Admin approves or rejects with one confirm, and Open
  on any row goes to the lead's full view (`?from=card-edits`, which its back link
  and the menu follow, as `?from=policies` does); a Team Admin sees their team's,
  read-only. A closer has no page of their own: the call and Callbacks show them
  where their request stands.
- **The fronter's details.** While the call is open, the Lead Details card
  (`QualificationSnapshot`) has Edit (`FronterDetailsDialog`,
  `PUT /interactions/{id}/details`).
  It reuses the fronter's `LeadCreateForm` and its checks, with the phone
  locked. Saving updates the lead for everyone and adds a qualification version.

## Own Sale

A closer with no transfer waiting starts a call of their own: no fronter, no
transfer. Own Sale on the Queue (closers only, styled as the fronter's New lead)
opens `components/closer/OwnSaleDialog.tsx`, and `lib/ownSale.ts` talks to the API.
The screens write it "Own Sale", the client's name for it.

- **Phone first.** `GET /leads/own-sale` checks the number: Do Not Call, or a number
  waiting in a transfer or already on a call (409 `own_sale.lead_busy`), shows on
  the phone field. A number already on the team fills the details step from its
  lead, with "Already a lead on your team since".
- **Then the details.** `LeadCreateForm` with the phone locked. Start sale
  (`POST /leads/own-sale`) goes to `closerWorkspaceHref(interaction_id)`, with no
  transfer id.
- **The call screen** loads a call with no transfer id by reading the call:
  `own_sale` on `GET /interactions/{id}` says it is an Own Sale call, and anything
  else shows "No active transfer". The header reads Own Sale, everything that
  waits on an accepted transfer opens, and Transfer Dropped is left out of the
  outcomes. The Task 6 lock and card edit approval apply as on any call.
- **The Queue** lists an open Own Sale call as an `own_sale` row whose `id` is the
  call, and an Own Sale callback has a null `transfer_id`; both open by the call.
- **The lead's full view** shows an Own sale event ("Started by <closer>, no
  transfer") where a transfer would be, and its
  details save as "Lead details saved", not the fronter's form.

## Reporting

`/admin/reports` reads `GET /reporting/funnel` through `fetchFunnel()` in
`lib/reporting.ts` for an inclusive range of business days: Leads, Qualified,
Transferred, Sold and Paid, counting the **leads added in the dates, each at the
furthest stage it has reached**. The card is titled "Lead funnel", so "conversion"
only ever means Team stats' paid over sales.

- **It counts leads, not interactions.** Each fronter form save opens another
  interaction and an uploaded lead has none, so interactions stopped matching
  leads; Attempts and Connects are gone. A lead counts once: Sold when any call's
  own latest closer outcome is a sale, Transferred when a closer accepted any of
  its calls (or it is sold), Qualified when its latest fronter outcome across all
  calls qualifies it (or it got further). So each bar sits inside the one before,
  and each is drawn as a share of Leads, with that share printed beside the
  count. Paid sits inside Sold: one of its sales has since been marked Paid by a
  monthly upload, in any month. ADR 0003 in the backend defines it all.
- **Qualified can read higher than Team stats' Qualified, and that is correct.**
  Team stats files a lead under its latest fronter outcome, so a transferred lead
  called back later sits under Callback there; here it has still reached
  Qualified. Transferred and Sold always match Team stats for the same dates.
- **Transferred doesn't claim the closer reached the lead.** The dialer bridge
  isn't recorded. The page says what each bar means in a line under the chart
  rather than in hover text, which a screen reader never reads.
- **No `timezone` is sent.** The server counts in the signed-in user's own zone
  (see Settings) and names it in the reply, and the page shows it beside the
  window as the abbreviation ("EDT", "PKT"). The page opens on today in the
  user's zone. If a reply ever names another zone and those days disagree, it
  corrects itself, staying on the loading state so a day nobody asked for is
  never drawn. A window the user picked is never corrected.
- **A Super Admin picks a team, or All teams; a Team Admin gets no picker.** The
  server keeps a Team Admin to their own team, so a picker would only offer a
  choice that 403s. The team list is `listTeams()`, read only for a Super Admin.
- **Every bar opens onto its own leads.** The bars are buttons; the selected one
  scopes the list beneath the chart, `FunnelLeads`, which reads
  `GET /reporting/funnel/{stage}` through `fetchFunnelStage()`. Leads is the
  default. A bar reading zero stays clickable, so a zero gets confirmed instead
  of wondered about. An empty window renders no list card at all, because the
  chart already says the range is empty.
- **The list is the funnel that came back, with the same team.** It sends the
  reply's `timezone` and the page's team, which is the only thing making its
  `total` the same figure as the bar above it; so it is handed the funnel that
  came back, never the range that was asked for. Its times are drawn in that
  zone too, with `formatZone()` as the caption.
- **A row is a lead:** name (the phone when there is none) and phone, team, date
  added, stage reached ("Added" for a lead that got no further), and its latest
  fronter and closer outcomes, `-` when there are none. Newest added first.
- **Only a Super Admin can open a lead,** through Open, which goes to
  `/admin/reports/lead/?id=…`. A Team Admin gets Summary in the same column:
  `LeadSummaryDialog`, reading `GET /leads/{id}/summary`, says who worked the lead,
  where it stands, the lead details the row doesn't show (vehicle, VIN, plate,
  source, who added it), and for a sale its policy number and when it sold. It
  has no card details, amounts or timeline: the API sends none.
  The row supplies the name, phone and stage, and the dialog is `dismissible`,
  because a read-only view has nothing to lose.

## Lead detail

`/admin/reports/lead/?id=…` reads `GET /leads/{id}/history` through
`fetchLeadHistory()` in `lib/leads.ts`: everything recorded on one lead, on one
page.

- **Super Admin only, twice:** `RequireRole role="super_admin"` and the API's 403.
- **Under `/admin/reports`, not `/admin/leads`,** so the sidebar's Reports item
  stays lit; Reports is its only way in, so the back link always goes there.
  `?id=` rather than a path segment, because the static export can't prerender
  one page per lead.
- **Top to bottom:** the lead card (two thirds) beside Where it stands, then the
  fronter's form beside each call's cart, then History. Lead information comes
  first because it is what a reader opened the page for; History is the long
  part, so it is last and paged.
- **Labels sit beside their values** (`Pairs` / `Pair`), never at the far ends
  of a wide card, and two pairs share a row where there is room.
- **Where it stands is the API's status, shown, not worked out here:** the
  waiting callback and the closer-on-a-call rule are the backend's own, so this page
  and the queues can't disagree. Waiting for a closer and On a call show only
  when they are true.
- **The form card shows what the lead card doesn't:** consent, DNC and any other
  answers, through the same `snapshotExtras()` and `snapshotValue()` as the
  interaction screen's Qualification panel, minus the lead's own fields
  (`ON_THE_LEAD`), which the form also carries.
- **A cart is masked, and a Super Admin can ask to see its full numbers.** Show
  full numbers calls `POST /interactions/{id}/cart/reveal` through
  `revealCartNumbers()` in `lib/cart.ts`, which the API records in the audit
  trail every time, so it is asked only on a click and never on load. The numbers
  swap in on the same rows and Hide numbers puts the mask back; a reload starts
  masked. There is no CVV to show: it is never stored.
- **History is a table, oldest first, ten to a page.** One line per event: time,
  what happened with its pills, the detail, and who. An outcome that replaced an
  earlier one on the same call says "Changed from …" rather than "Corrected": a
  worked callback is saved as the call's next version just like a correction, and
  the API can't tell them apart.
- **History leaves some things out on purpose.** Form saves and offers that timed
  out stay on record and in the API, but `shownInHistory()` in `lib/leads.ts` keeps
  them off the table. This page also never names a lead's calls: they are how the
  app groups saves, not something a reader needs.
- **Not here, because nothing records it:** a callback's time or owner (callbacks
  go to the whole team), and dialer data such as call legs and raw events, which
  stay on the interaction detail screen. Reports no longer links there.

## Team stats

`/admin/team-stats` reads `GET /reporting/teams` through `fetchTeamStats()` and
`GET /reporting/sales` through `fetchSales()`, both in `lib/reporting.ts`. Super
Admin only, in all three places: the sidebar item, `RequireRole
role="super_admin"`, and the API's 403.

- **The team table counts the leads added during the dates, and where each one
  stands now.** Each lead counts once: Callback and Qualified by its
  latest fronter outcome, Transferred if a closer accepted a transfer on any of
  its calls, Sold if the latest closer outcome on any of its calls is a sale. A
  range's figures keep moving as its leads are worked. An "All teams" row sits
  under the teams.
- **Conversion is Paid over Sales,** both by date, not by the leads added: the
  sales paid during the dates (a paid month counts on its 1st) over the sales
  made in them. A cell shows the rate, a bar to compare teams by eye, then
  "12 of 40". Old sales paid now can take it past 100%, and the rate is shown as
  it is; only the bar stops at full. "n/a" means no sales. This month reads low
  until its file is uploaded, the month after, and the note under the table says
  so. The two tiles say which they count, "of the leads added in these dates" and
  "sales made in these dates", since Sold and the sales can differ by a lead added
  in the range but sold after it.
- **The sales list goes by the day of the sale**, not the day the lead came in,
  so its count can differ from the table's Sold. Newest first, paged on the
  server (`ServerPaging`, 50 to a page), with totals across every matching sale.
  A sale with no cart shows `-` for its amounts and adds nothing to the sums. No
  card values or policy number come back. A Paid column shows the month it was
  marked Paid in, or `-`.
- **The agent filter belongs to the sales list**: closers from `listUsers()`,
  narrowed to the chosen team's. Changing the team resets it, and changing any
  filter goes back to the first page. The list loads and fails on its own, so a
  sales error never hides the team table.
- **The page opens on this month so far** (`monthToDate()`) and, like Reports,
  sends no `timezone`. It needs no correction step, because the user's zone is
  set before the page renders.
- **The filters have a card of their own at the top**, shared by the table and
  the sales list. Tiles carry the totals. The team table is shown whole
  (`paginate={false}`), the Team column takes the slack (`width` on its column),
  the "All teams" row is shaded and bold, and a team with no leads in the range
  is drawn in grey.

## Agent stats and My Stats

Each agent's figures for a day, a week or a month, and the targets Team Admins
set. `lib/agentStats.ts` talks to the API, and the pieces both screens share live
in `components/stats/`.

- **The period** is `PeriodPicker`: Today, Week or Month, and arrows back through
  earlier ones, never past today. Weeks run Monday to Sunday. The arrows send a
  day just outside the period shown and the server works out the period, so the
  label always comes from the dates it answered with. Switching tabs goes back to
  the current period.
- **Paid and Conversion are monthly, and a closer's.** A sale is Paid in the
  month its upload names, so they show on the Month tab only; Today and Week say
  so in their place, and the Paid list is offered on a month only (the API
  refuses it otherwise). A fronter has no Paid anywhere, on Agent stats either,
  and their policy list is Sold only.
- **My Stats** (`components/stats/MyStatsScreen.tsx`, used by both
  `app/fronter/stats` and `app/closer/stats`) reads `GET /me/stats`. A fronter
  sees Qualifications, Transfers, Callbacks and their target; a closer
  Sold, Paid, Conversion, Cancelled, Retained, Pending, the average QA score and
  their target. A closer also gets `AgentSalesTable`, their Sold, Paid and
  Cancelled policies with policy number, status, paid month, QA score and QA
  notes, and no amounts. Today's outcomes (`GET /me/stats/today`) show under them
  on the current day only.
- **Agent stats** (`/admin/agent-stats`, `components/admin/AgentStatsScreen.tsx`)
  is for Team Admins and Super Admins (`RequireRole role="administrator"`).
  Filters: Team (Super Admin only), Agent, Fronters or Closers, and the period,
  all in the URL so Back from a lead returns to the same view. All agents is a
  table with their figures and target; picking one (View or the Agent filter)
  shows their tiles, `AgentLeadsTable` and `AgentSalesTable`. A Team Admin sees
  only their team and no amounts; a Super Admin also gets Total, Down and
  Monthly on the sales.
- **A lead opens as Reports opens one**: the full view for a Super Admin, with
  `?from=agents` so the menu and back link say Agent stats, and
  `LeadSummaryDialog` (no stage badge here) for a Team Admin.
- **Targets** (`AgentTargetsDialog`) are daily, weekly and monthly, qualifications
  for a fronter and sales for a closer, blank for none, set from the table or the
  agent's view. Each period's figures carry its own target. Agents see their
  progress and never edit it.

## Exceptions and interaction detail

`/admin/exceptions` works the reconciliation queue through `lib/exceptions.ts`;
`/admin/interactions/[interactionId]` is the record behind a row, read through
`lib/interactionDetail.ts`. Exceptions is open to every administrator; the
detail screen is Super Admin only.

- **Reconciliation makes no call to VICIdial.** It is a self-consistency audit of
  the CRM's own tables against the raw event inbox, swept every five minutes by
  the backend worker. Two reasons exist: `multi_leg_without_transfer` (two or
  more call legs and no transfer row of any status) and
  `late_event_after_finalization` (an event arrived more than the grace window
  after the interaction was dispositioned). The Issue column is human copy from
  a `Record<ExceptionReason, …>` in `lib/exceptions.ts`, so a third reason fails
  the build here rather than reaching the screen as its enum.
- **`details` is the only place the evidence appears**, and the expanded row is
  the only place `details` is rendered. That is the point of the screen: the
  reviewer sees what the sweep saw without leaving the row. Its shape follows
  `reason` and nothing else publishes it.
- **Resolving records a judgement, not an observation.** These mismatches cannot
  heal — an interaction with two legs and no transfer still has both tomorrow —
  so the sweep leaves a resolved row alone instead of reopening it every five
  minutes. The copy on screen says so. Reopening clears the note with the
  timestamp, as the API does.
- **The list defaults to outstanding.** `resolution` is `open` | `resolved` |
  `any`, not a boolean: a tri-state boolean cannot say "either" in a query
  string. The queue pages against the server (`limit`/`offset`) rather than
  reading whole the way `/admin/users` does — a staff roster is bounded and an
  exception queue only grows while nothing is resolved.
- **An empty Call Legs table is correct, not a bug.** Nothing populates
  `call_legs` while the dialer's push carries no call id, so live interactions
  record none; the panel says that in a line rather than leaving a bare "No
  rows". The Raw Event Log says the matching thing: empty means none were
  *recorded*, never that none arrived.
- **Nothing on these screens is fabricated.** Where the backend has no data the
  panel is empty and explains itself. This is the screen an administrator opens
  precisely because they do not trust the data; invented rows with plausible
  timestamps would be indistinguishable from real ones.
- **The detail screen carries no exception chrome.** No reason badge, no
  resolve control. The back link is driven by `?from=`, mapped in one `ORIGINS`
  record in `components/admin/InteractionDetailScreen.tsx`, `exceptions` only
  since Reports opens leads instead; a new caller adds its entry and passes the
  param. An unrecognised or absent `from` falls back to the dashboard, which is
  what a bookmarked link gets.
- **It is a lead's full view, so it is the Super Admin's alone.** The API
  refuses a Team Admin the interaction, its dispositions, its qualification, a
  single transfer and the three panels, and the page sits behind
  `RequireRole role="super_admin"`.
  Its way in, "Open interaction detail" on an exception, shows for Super Admins
  only; a Team Admin keeps the rows.
- **It lights no sidebar item.** `isActive` for Exceptions matches
  `/admin/exceptions` only. The back link is what says where the reader came
  from, which is the same `?from=` the heading is built out of.
- **Times here name the zone they are drawn in**, because these answers carry
  no business zone the way `/reporting/*` does. They are instants, not business
  days — but a bare local-time string would read as one, which is the confusion
  `/admin/reports` already had to fix. A single timestamp says it inline
  (`formatInstant`); a table of them says it once beside the card title
  (`localZoneName`), because repeating it in every cell costs more width than
  the data and pushes columns into each other.
- **A table whose cells must not wrap passes `minWidth` to `DataTable`.** MUI
  lays tables out fixed — it divides the width it is given and ignores the
  cells — so without it a `whitespace-nowrap` id simply overlaps the next
  column. With it the table is measured by its content and the card scrolls.
- **`GET /interactions/{id}` has one caller**, `getInteractionDetailResponse()`
  in `lib/interactions.ts`, which the workspaces and this screen share.
  `lib/interactionDetail.ts` holds only the three panel reads and the
  admin-side qualification read, which that file has no reason to know about.
  A missing interaction arrives as `InteractionNotFoundError`, not an
  `AuthError` — branch on the type, not on a code string.

## Users

`/admin/users` administers accounts through `lib/users.ts` — `GET /auth/users`
to list, `POST` to add, `PATCH /auth/users/{id}` to change a name, roles,
state or team. Administrator-only, like the rest of `/admin`.

- **There is no delete.** Deactivating is `PATCH {active: false}`, and it
  revokes that person's refresh tokens as it commits: they are signed out on
  their next request, not at their next login. The wording on screen says so.
- **A username cannot be changed.** `UpdateUserRequest` carries name,
  roles, active and `team_id`, and nothing else. The field is shown disabled
  rather than hidden, so nobody goes looking for it.
- **Team is set by a Super Admin.** They must pick it when adding and can change
  it when editing; the edit sends `team_id` in the same PATCH as the rest, and
  only when it changed. Super Admin, QA Manager, QA Agent and Retention accounts
  have no team: ticking any of those roles makes it the only one and hides the
  field, and `qa_manager`, `qa_agent` and `retention` are fixed once the account
  exists. Only a Super Admin adds a Retention account. A QA Manager
  only adds QA Agents, so never picks a team. Picking a different team shows a note that the move takes
  effect on save and that anyone on a call should record its outcome first. The
  API does not block a move mid-call. Team Admins never see the field: the API
  puts their users on their own team and refuses `team_id` from them.
- **Creating a user sets a username and a password.** The username is checked
  against the API's rule (3 to 64 letters, numbers, dots, dashes or
  underscores) before sending. The invitation-link option is gone from the
  form; the API and the `/invite` page still handle one for an account that
  has an email.
- **Email is optional, only for Forgot password, and the Super Admin's.** Only a
  Super Admin sees the Email field, on Add and Edit user: whoever holds the email
  can reset the password, and only the Super Admin resets passwords. Team
  Admins and QA Managers add by username and password alone. Clearing it sends
  `email: null`; leaving it untouched leaves the key out. No other screen shows
  an email.
- **Roles are checkboxes, not a picker**: `roles` is an array in every DTO and
  someone may hold more than one. The list comes from a `Record<Role, string>`
  in `lib/users.ts`, so a role added to the contract fails the build here rather
  than quietly missing from the form.
- **You cannot demote yourself.** The API refuses with
  `user.cannot_demote_self`; the form disables your own Administrator and Active
  controls and says why, so the refusal is never a surprise.
- Failures land on the input they name: the API's `fields` array is mapped onto
  the matching control (a duplicate username shows under Username), and anything
  unnamed falls back to the dialog's `<Alert>`.
- **A Super Admin can reset someone's password** from Edit User's Password
  section, which switches the same dialog to a reset step (Back keeps any unsaved
  edits): `PUT /auth/users/{id}/password` with a password they type and tell the
  person. Every session that person has ends, so they are signed out within the
  15-minute access token. Super Admin only, and never your own account
  (`user.cannot_reset_own_password`); your own goes through Settings.

## QA

QA reviews sales, company-wide: QA Managers and QA Agents have no team. Every
sold call is a QA item, through `lib/qa.ts` (`/qa/items`, `/qa/summary`,
`/qa/agents`, `/qa/stats`, and the assignee and status routes).

- **Who sees what:**
  - a Super Admin and a QA Manager see every team at `/admin/qa`: count tiles for
    all teams together, a Teams table with each team's counts (its name filters
    the queue), then the queue;
  - the count tiles are the Users screen's `StatCard`, in the order the work goes
    (Unassigned, Open, Disputed, Resolve Dispute, Closed). Each one filters the
    queue, and clicking the selected one clears it. Unassigned means open and
    nobody has it, the same as the API's `assignee=none`;
  - a QA Agent sees only the open sales assigned to them at `/qa`, as "Assigned
    to me", with no filters. Once they close or dispute one it leaves their queue
    and its page answers them 404. They never call `/qa/summary` or `/qa/agents`,
    which answer them 403.
- **Assigning** is the QA Manager's and the Super Admin's, from the "Assigned to"
  dropdown in each row or on the sale page, which saves on change. Only an open
  sale can be assigned, to any active QA Agent; after that it shows as text.
- **The flow** has two paths, Open to Closed and Open to Disputed to Resolve
  Dispute, and both ends are final. `movesFor()` mirrors the API: the assigned
  agent gets Close and Dispute on an open sale, a Super Admin gets Resolve
  dispute on a disputed one, and nobody else gets a button. A QA Manager never
  moves a sale.
- **The sale page** (`/admin/qa/item?id=`, `/qa/item?id=`) is `QaItemScreen`,
  laid out around what the reviewer checks:
  - a header with the lead's name, the team, who sold it and when, and the
    status pill (and "Open lead" to the full record, for a Super Admin);
  - on the left, two cards: the lead's details (`LeadCard`), and Sale, which
    starts with the closer and when they sold it, since that is how the agent
    finds the call recording, then this sale's own cart, masked (`CartCard`
    from `LeadDetailScreen`, with a `title` and a `before` row), or "No cart was
    saved for this sale". The API sends QA nothing else from the lead, and only
    a Super Admin gets "Show full numbers";
  - on the right, a panel that stays in view, with one job per person. The
    assigned agent gets "Your review": a 0 to 100 slider that starts unscored
    (a hollow thumb and "Not scored yet", so nothing closes on a default),
    optional Notes, then "Close with score N" (disabled until scored) and a red
    Dispute that takes a score or not. A Super Admin on a disputed sale sees the
    agent's verdict, score and notes, and Resolve dispute. Anyone else sees the
    verdict once there is one, and the QA Manager and Super Admin the "Assigned
    to" picker while the sale is open;
  - at the bottom, Review history (who assigned it, who moved it, when, the notes
    and the score, read back from the audit trail), folded away for an agent and
    open for everyone else.

  After an agent's move the page goes back to their queue.
- **QA stats** (`/admin/qa/stats`, `/qa/stats`) is `QaStatsScreen`: a
  Today | This week | This month switch with the days and zone the figures cover
  beside it, right above them (`Segmented` in `components/ui`; ranges from
  `businessDay`, `weekToDate` with weeks from Monday, and `monthToDate`). Then
  three `StatTile`s, Reviewed, Closed and Disputed (with its share of
  reviewed), added up on screen: an agent's own, or every agent's together.
  There is no score here: it grades the closer's sale, not the agent's work,
  and belongs to the closers' stats. The QA Manager and Super Admin also get
  Custom, which opens the `DateRangePicker` Team stats uses, and a table
  comparing agents: most reviewed first, Disputed with its share, agents with
  no reviews greyed, and an All agents row. A review counts on the day the agent
  closed or disputed the sale, in the user's own zone. The client asked for
  daily, weekly and monthly figures for the agent targets, so the same three
  presets keep the stats pages alike.
- **Mocks** keep a fixed set of five sales per team in memory; each lead id is one
  `mockLeadHistory` reads as sold, so a sale opens onto its lead and cart. Quinn
  QA (QA Manager), Aria Agent and Leo Lead (now a QA Agent) have no team and
  sign in with `password1`. Aria has one dispute and one close from today, so the
  stats have figures.

## Policy lookup and Paid policies

`/admin/policies` (Team Admin and Super Admin) takes a CSV or Excel file with one
policy number per row and shows the sale behind each, and whether it is Paid,
through `lib/policies.ts` (`POST /reporting/policy-lookup`). The lookup saves
nothing. A Super Admin then marks the matches Paid for a month.

- **The API reads the file:** the first column, a header row and blank rows
  passed over, case and surrounding spaces ignored, up to 5,000 numbers and 1 MB.
  A file it cannot read comes back as a 422 naming `file`, and its message shows
  under the upload. A Team Admin only finds their own team's sales; another
  team's reads as not found.
- **The upload** is one drop zone (`PolicyFileDrop`, shared with Retention's
  upload): drag a file in, or Choose file, then Look up.
- **Results** have a header naming the file, then three `StatCard` tiles,
  Matched, Not found and Skipped, that each show their own table, 20 to a page in
  the browser. Matched shows each lead's phone; a Super Admin also sees the team,
  the amounts and an Open button for the lead's full view.
- **A Team Admin gets no amounts and no download.** The API sends their amounts
  as null, and each match has Summary instead of Open: the same
  `LeadSummaryDialog` as Reports.
- **Download results** is the Super Admin's, built in the browser
  (`policyResultCsv`): every uploaded number with its status, lead, phone and
  sale, in the upload's order, so no row column is needed. It starts with a byte
  order mark so Excel reads it as UTF-8, and a cell a spreadsheet would run as a
  formula gets a leading apostrophe.
- **Matched shows a Paid column** for both roles: the month, or "Not paid", and
  a Policy status column, as Retention set it. The same two show in Team stats'
  sales list and on a lead's cart.
- **Mark as Paid is the Super Admin's next step** (`MarkPaidPanel`), between the
  tiles and the tables once a lookup has matches. They choose the month (this one
  and the 23 before it, no default), read what will happen ("42 sales will be
  marked Paid. 8 are Paid already and keep their month."), and confirm in a
  dialog. `markPaid()` sends the same file and the month to
  `POST /reporting/paid-uploads`, and the API reads it afresh. It can be saved
  when every match is already Paid, since those matches are what an undo falls
  back to. Afterwards the lookup is read again, so the Paid column shows the new
  month, and the panel becomes "Saved as the October 2026 upload" with no button,
  so one lookup is never saved twice. A new lookup brings the panel back.
- **The first upload wins.** A sale keeps the month of the earliest upload still
  standing that matched it; a repeat upload or a later month never moves it.
- **A sale made after the month is left out**, since it cannot have been paid in
  it. The panel counts it out once a month is chosen and says so, and Mark as
  Paid stays off when nothing is left.
- **Paid uploads** (`PaidUploadsSection`, Super Admin only, under the lookup)
  lists every upload newest first: month, file, matched, newly paid, who and
  when. Undo asks first, then the sales it marked go back to unpaid, or to the
  next upload that matched them. An undone upload stays, as "Undone by ...". After
  an undo the lookup on screen is read again, and if it was that upload's, its
  panel resets.
- **The file stays with the cached lookup**, in memory only, so coming back from
  a lead can still mark it.
- **Mocks** know `POL-10001` to `POL-10030`, spread across the mock teams. An
  Excel upload gets a fixed sample answer, since the mock does not unpack it.
  Paid uploads live in memory with the first-upload-wins rule, and a marked sale's
  lead reads as Paid on its full view.

## Retention

`/retention` (Retention) and `/admin/retention` (Super Admin) record each sale's
policy status, Pending, Retained or Cancelled, through `lib/retention.ts`. The screens
take their link base, so both desks share them.

- **A status belongs to the sale,** and a policy number to one sale, so the
  number is how it is found. A sale has none until one is set. Conversion, the funnel and Paid never
  read it: a cancelled policy stays Paid.
- **Pending and search** (`RetentionScreen`): find a sale by its whole policy
  number, in any case, which opens it, and below, the policies that are
  Pending, the longest since their last change first. Nothing else is listed, so
  Retention never browses the sales.
- **A sale** (`RetentionSaleScreen`): the customer, phone, vehicle, team, closer
  and sale date, the status history newest first (who, when, the note, typed or
  which file), and QA's review with `ReviewHistory` from the QA screen. Never
  the paid month, amounts or bank details: the API never sends them. The panel
  sets the status, with an optional note.
- **Upload** (`RetentionUploadScreen`): the template is
  `public/retention-template.csv`. The API finds the columns by their headings,
  one with "policy" in it and one with "status", and reads "Canceled" and
  "Retention" as Cancelled and Retained. Check saves nothing and shows five
  tiles: Changes, No change, Not found, Invalid status and Skipped. Save asks
  first and saves only the changes, checked afresh.
- **Mocks** keep the history in memory, with POL-10002 and POL-10003 Pending and
  POL-10005 Cancelled to start, and `rita.retention` signs in as Retention.

## Settings

`/admin/settings`, `/fronter/settings` and `/closer/settings` all render one
`SettingsScreen`, so each desk keeps its own nav around it. The Settings row in
the sidebar's bottom section links to the current desk's page.

- **Time zone.** Eastern (`America/New_York`) or Pakistan (`Asia/Karachi`),
  saved with `PATCH /auth/me`. Every formatter in `lib/format.ts` draws in it,
  and the server counts "today" and report days in it. `CurrentUserProvider`
  sets it before rendering and keys its children by it, so saving a new zone
  redraws every screen. Eastern shows as EDT or EST on its own; Karachi is
  labelled "PKT" by `zoneAbbreviation`, because Intl calls it "GMT+5".
- **Password.** `POST /auth/password/change` with the current one. The API ends
  every session and hands this device a new pair, which `changePassword` in
  `lib/session.ts` stores while holding the refresh lock, so no renewal can
  send the old token in the meantime. Another signed-in device still holds an
  ended token, and its next refresh makes the API end every session, this one
  included: the success message says the user may need to sign in again here.

## Campaigns

`/admin/campaigns` keeps the campaign catalogue through `lib/campaigns.ts` —
`GET /campaigns` to list, `POST` to add, `PATCH /campaigns/{id}` to change one.
Super Admin only.

- **A campaign here is a name and the teams that work it** — none, one or
  several. The API can also carry a VICIdial routing key (`match_type` +
  `match_value`); it is optional, this screen never shows or sends it, so a
  campaign that has one keeps it through an edit.
- **One call saves everything.** Add and edit send `team_ids` with the rest, and
  an unknown team fails the call with nothing saved. `PUT /campaigns/{id}/teams`
  exists, but this screen has no use for it.
- **There is no delete.** A campaign is retired by turning Active off.
- **Names are unique**, compared exactly once trimmed; a clash comes back as
  `campaign.already_exists` against `name` and shows under the field.
- Team Admins can read their own team's campaigns through the API, but there is
  no screen for that yet.

## Leads

`/admin/leads` lets a Team Admin put leads on their team through `lib/leads.ts`:
`GET /leads` to list, `POST /leads` to add one, `POST /leads/bulk` to upload a
CSV. Team Admin only: the page is guarded with `exact`, so a Super Admin does not
inherit it, and their desk has no Leads item.

- **A new lead goes straight onto the team's fronter queue.** No fronter-side
  work is needed; the queue's own refresh picks it up.
- **Add Lead checks for the number first.** `POST /leads` answers 201 whether it
  created the lead or found one the team already has, so the form asks
  `GET /leads?phone_normalized=` before saving, and says so when it is a repeat.
- **The name only labels the queue row.** It is not stored on the lead, so the
  list and the Active Call screens show the phone. A blank name is left out of
  the request, because the API refuses an empty one.
- **The campaign picker follows the API's rule:** no field when the team has no
  active campaign (the queue says "Manual upload"), the one campaign already
  picked, or a required choice when there are several.
- **Upload CSV is multipart.** `uploadLeads` builds the form data on every call
  and sets no `Content-Type`, so the browser writes the boundary. Only a file
  named `.csv` is taken: the picker's filter can be switched off, and Excel on
  Windows labels a CSV as a spreadsheet type, so the name is what is checked.
  The API takes up to 1,000 rows and 1 MB and answers per row. The results are
  three counts (added, already on your team, could not be added) and a table of
  every number that was not added, by line number, with the reason: already on
  your team, invalid, do-not-call, or repeated in the file. Uploading the same
  file again is safe: rows already added come back as already on the team and
  are not queued twice.
- **The template is `public/leads-template.csv`:** the header and one example
  row on a reserved 555-01xx number, saved as UTF-8 with a byte-order mark so
  Excel opens it cleanly. The API accepts the mark.

## Emailed links

`/invite/[token]`, `/reset-password/[token]` and `/forgot-password` are how a
password gets set without a Super Admin, and only for an account with an
email; everyone signs in by username. The first two are one component,
`components/auth/SetPasswordScreen.tsx` with a `mode`, and all three call
`lib/invitations.ts`.

- **The token goes in the request body, never the URL.** The API is built that
  way so a live credential stays out of access logs; a call that put it back in
  a path would undo it. The page reads it from its own address and posts it.
- **These pages have no session**, so they sit outside `RequireRole` and outside
  `withSession` — the one place in `lib/` that calls `fetch` without it. There
  is nothing to renew.
- **Forgot-password must never reveal whether an address exists.** The API
  answers 202 for an unknown or deactivated address exactly as for a real one,
  and the screen shows the same confirmation either way. "No account with that
  email" would hand back precisely what the API withholds.
- **A refused link explains itself instead of showing a form.** `.superseded`
  says a newer email exists, `.already_redeemed` offers sign-in, `.expired` and
  an unknown token offer a fresh one. A link can also go stale between opening
  the page and submitting, so 404/410 on submit falls into the same state.
- **Both accepts return a session**, so the user lands on their desk signed in
  rather than at a login form typing the password they just chose.
- Mock handlers seed four tokens — `live-link`, `expired-link`, `used-link`,
  `superseded-link` — and a newly issued invitation logs its URL to the console,
  the mock equivalent of the backend's `log` transport.

## Copy and paste

`components/auth/CopyGuard.tsx`, mounted once in `AppProviders`.

- **Everyone but a Super Admin types every form by hand.** Once signed in, copy,
  cut, paste, right-click, text selection and dragging do nothing, and nothing on
  screen says so.
- **Two things still work:** paste into a password field, for password managers,
  and dropping a file onto an upload. The sign-in, invite, reset and
  forgot-password pages are left alone.

## Screenshots

`components/auth/ScreenGuard.tsx`, mounted next to CopyGuard, for the same people
(`useGuarded()`).

- **The whole page blurs** while Alt or the Windows key is down, while the window
  is out of focus and while the tab is hidden. That beats Alt + Print Screen,
  Win + Print Screen, Win + Shift + S and the Snipping Tool.
- **A plain Print Screen can't be beaten:** Windows takes the image before the
  page hears the key. Its release calls `POST /auth/me/screenshots` with the page,
  and the agent sees "Screenshot recorded". No screen shows the log yet.
- **The blur is an overlay** (`.screen-guard-overlay` in `styles/globals.css`),
  shown by `data-screen-blur` on `<html>`, which the listeners set directly so it
  lands on the next frame. A filter on the page would move fixed elements.
- **Selection is CSS.** The guard sets `data-copy-guard` on `<html>`, and
  `styles/globals.css` turns selection off under it, except inside fields, where
  correcting what was typed needs it.
- **Autofill is off for every role.** `Input` and `Textarea` default
  `autoComplete` to `off`; only password and sign-in fields name their own.
- **It discourages, it doesn't prevent.** Developer tools get around it, and no
  website can stop a screenshot.

## UI conventions

- **MUI is the component layer; Tailwind is for layout/spacing utilities.**
  Shared primitives in `components/ui/` wrap MUI (`Button` → `MuiButton`,
  `Input`/`Select`/`Textarea` → `TextField`, `Checkbox`, `Alert`, `Badge` →
  `Chip`, etc.). Prefer those wrappers over raw MUI or native HTML controls;
  extend them with props rather than duplicating styles. Feature tables and
  form composites may import MUI directly (`Table`, `RadioGroup`, …) when no
  shared wrapper exists yet.
- Theme lives in `lib/theme.ts` (`createTheme` + `tokens` mirrored from Figma /
  `tailwind.config.js`). Wired in `app/providers/AppProviders.tsx` via
  `AppRouterCacheProvider` (`prepend: true` so Tailwind `className` utilities
  still beat Emotion) + MUI `ThemeProvider`. Do **not** set `enableCssLayer`
  — that path is for Tailwind v4; on v3 it makes every MUI style lose to
  preflight.
- Visual theme (as of the Figma "CRM - Auto Warranty" file, superseding the
  earlier dark/teal theme): light (`bg-paper` / `tokens.paper` `#FCFCFC`),
  `ink` (`#1C2430`) for headings/dark surfaces, `navy` (`#1F3A5F`) for
  primary CTAs on default desks (see the accent note below), `slate` (`#8A94A3`) for borders/placeholders/secondary text.
  `status-red` / `status-green` / `status-gold` / `status-blue` are
  accent/status colors only, not for primary CTAs. Keep `tokens` in
  `lib/theme.ts` and Tailwind color keys in sync when adding colors. Font is
  Inter, loaded via `next/font/google` in `app/layout.tsx` (`--font-inter`),
  on a 61/49/39/32/23/20/18/16/14/13px type scale (base 16, ~1.125 ratio,
  120% line-height). `Button` takes a `variant` prop (`primary` accent-filled /
  `secondary` slate-outlined) and a `size` prop (`default` / `small`).
- **The accent follows the desk.** Team Admin is green, Fronter yellow, Closer
  orange; Super Admin and the QA desks keep navy. `styles/globals.css` is the
  only place the role colours are written, as `--accent*` tokens. `Sidebar` sets
  `data-accent` on `<html>` from `deskAccent()` in `lib/auth.ts`, on `<html>`
  because dialogs and menus render under `<body>`. The accent reaches primary
  buttons, the sidebar and the page header rule, and nothing else: links, focus
  rings and status pills keep their colours. MUI's `palette.primary` stays navy
  on purpose, because radios and other MUI parts read it and yellow on white
  fails contrast. Accents are deep fills with light text, like navy, except
  yellow, which turns olive when darkened, so it stays light and takes navy
  text. Use `--accent-text`, never `--accent`, for text on white.
- Errors (auth failures, form validation) render inline via `<Alert>` /
  `role="alert"` — never fail silently or let an unhandled rejection crash
  the page.
- The dashed card (`rounded-xl border-2 border-dashed border-relay-blue`) marks
  something live going on. The fronter queue and the closer's qualification
  snapshot always use it; the admin dashboard's Agent Status card switches to
  it only while someone is on a call — drawn there as an outline, which takes no
  room, so switching never moves the table.

## Route-segment conventions (App Router)

Segments should carry their own `layout.tsx` for segment-specific metadata
(see `app/login/layout.tsx`) rather than leaving everything to the root
layout. Follow this pattern for new top-level routes that need their own
`<title>`.
